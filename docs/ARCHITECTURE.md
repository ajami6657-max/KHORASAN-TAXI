# معماری سامانه

## محدوده محصول
پلتفرم چنداستانی برای خراسان رضوی، شمالی و جنوبی. استان، شهر، محدوده خدمت و تعرفه باید داده‌های قابل مدیریت باشند؛ شهرها نباید فقط در منطق برنامه hard-code شوند.

## اجزای منطقی
1. Passenger Android: حساب، مبدأ/مقصد، برآورد کرایه، درخواست، پرداخت، پیگیری و ارزیابی.
2. Driver Android: احراز هویت، مدارک خودرو، وضعیت آماده‌به‌کار، پیشنهاد سفر، ناوبری و درآمد.
3. Admin Panel: مدیریت استان‌ها، شهرها، کاربران، رانندگان، سفرها، تعرفه‌ها و شکایت‌ها.
4. Backend API: منبع حقیقت برای هویت، قیمت، تخصیص سفر، وضعیت و تراکنش.
5. Realtime Gateway: انتشار موقعیت و تغییر وضعیت سفر با کنترل دسترسی.
6. AI Assistant: پاسخ عمومی آفلاین؛ داده زنده سفر و پرداخت فقط از API مجاز و آنلاین.

## جریان سفر
درخواست مسافر → اعتبارسنجی محدوده خدمت → محاسبه کرایه سمت سرور → پیشنهاد به رانندگان واجد شرایط → پذیرش → انجام سفر → ثبت تراکنش و رسید.

## مدل داده اولیه
- Province(id, name, code, enabled)
- City(id, province_id, name, enabled)
- ServiceArea(id, city_id, geometry, enabled)
- User(id, phone, role, status)
- DriverProfile(user_id, verification_status)
- Vehicle(id, driver_id, plate_hash, type, status)
- Ride(id, passenger_id, driver_id, origin, destination, status, fare_quote_id)
- FareRule(id, city_id, service_type, parameters, active_from)
- Payment(id, ride_id, amount, currency, status, provider_reference)

- احراز هویت و مجوزدهی در سمت سرور انجام شود.
- قیمت نهایی و وضعیت پرداخت از کلاینت پذیرفته نشود.
- مختصات زنده فقط برای افراد مجاز همان سفر نمایش داده شود.
- مدارک هویتی رمزگذاری و دسترسی به آن‌ها محدود شود.
- کلیدهای سرویس در Git ثبت نشوند.
